# Repository documentation for v1.0.1

The owner approved a documentation patch to the AWS starter. The distribution at tag `v1.0.0` is the baseline. The [project brief](../../project/brief.md) establishes consultation, preservation and operational authority. This work covers the conventions a developer receives and the README that explains the starter. The review and verification apply to one local candidate.

| ID | Required behavior | Acceptance criterion | Scope |
| --- | --- | --- | --- |
| REQ-001 | WHEN a project receives a fresh structure record, THE starter SHALL provide editable repository conventions at the mapped structure path. | A fresh template copy and a separate greenfield installation contain guidance on hierarchy, ownership, naming, numbered specifications, work-scoped identifiers and cross-references, evidence provenance, language-specific choices, infrastructure, security, costs, operations, decisions, diagrams, governance and semantic versioning. | Required |
| REQ-002 | WHEN a project already owns a structure document, THE installer SHALL preserve its contents and canonical location. | Conventional and explicitly mapped brownfield documents retain their original bytes and path. An upgrade from v1.0.0 preserves both the stock structure record and a separately tested customized record. | Required |
| REQ-003 | WHEN a developer opens the generated repository README, THE guide SHALL show how to start and continue work from the distributed application. | The guide covers GitHub template creation, Codespaces and Codex prerequisites, the literal kickoff `start`, all seven shortcuts, public toolkit guidance, optional AWS Emulator, and permission boundaries for credentials, costs, additional model calls and cloud delivery. | Required |
| REQ-004 | WHEN a developer first encounters the lifecycle, THE README SHALL explain how six named artifacts connect an intended outcome to observed evidence in a single illustrative appointment-booking retry. | The initial tree matches the package and the populated example is explicitly illustrative. For each requirement (REQ), design (DES), correctness property (PROP), implementation task (T), verification check (CHK) and evidence record (EV), give its full name and ID prefix, plain-language meaning, the question it answers, usual storage location, a practical example and its relationship to the other records. Use descriptive diagram labels. Throughout the example distinguish intended behavior, the approach and implementation work, the verification procedure and the observed result. | Required |
| REQ-005 | WHEN an existing-project developer follows the adoption and governance guidance, THE guide SHALL identify the executable preview and apply steps and the authority for project work. | Commands use the installed bootstrap path. The guidance distinguishes the canonical task ledger from optional mapped trackers, explains maintenance and distribution branches, versioning, contributions and security reporting, and makes no promise of automatic tracker synchronization. | Required |
| REQ-006 | WHEN the documentation patch is presented for release preparation, THE release record SHALL identify the verified local candidate and the scope of its evidence. | The maintainer README, application README and changelog agree on the version and verification boundaries. Deterministic builds, structure/link and anchor checks and the full offline regressions identify this candidate. Historical native observations identify v1.0.0 and its frozen inputs. Promotion remains an owner decision. | Required |

The recommended style for documents and directories is lowercase kebab-case where existing platform or language standards permit it. Existing application owners retain their architecture and standards. The approved patch changes generated Markdown and documentation, with local tests and receipts. Existing runtime semantics, dependencies, directory structure, remote refs and the v1.0.0 tag are outside the change surface.
