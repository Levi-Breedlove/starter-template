# Requirements: complete developer workflow

**Scope:** A usable specification-driven AWS development workflow for greenfield and brownfield projects, implemented through Codex and a small local tool layer.  
**Authority source:** The repository owner requested an execution plan and repository implementation after reviewing concrete workflow gaps.  
**Product constraint:** Preserve neutral repository content and existing official AWS plugin identities. Existing architecture, instructions, project data and delivery ownership remain authoritative.

## Outcome

A developer can adopt the package, describe a goal, receive guided consultation, review structured specifications, execute an authorized task plan, reconcile changes, and continue with trustworthy records. The implementation must distinguish generated proposals, actual model judgments, executed checks and observed external outcomes.

## Behavioral requirements

| ID | Condition and required outcome | Acceptance criterion | Required or deferred |
| --- | --- | --- | --- |
| REQ-001 | WHEN a developer starts without active work, THE workflow SHALL report setup readiness and direct the agent to the mapped application consultation records. | Read-only setup check works before selection; source and adopted paths are correct; no invented work item, account inspection or model call. | Required |
| REQ-002 | WHEN a new structured feature is specified, THE workflow SHALL support explicit EARS patterns and identify malformed required statements without claiming semantic proof. | Ubiquitous, event, state, unwanted, optional and combined patterns are documented and exercised; existing contracts remain compatible. | Required |
| REQ-003 | WHEN requirements analysis is requested, THE workflow SHALL produce a source-bound review request and validate the actual returned findings before recording them. | Structured analysis, required source identities, material blockers, malformed responses and stale results are handled; semantic judgment is labeled as model or human review. | Required |
| REQ-004 | WHEN a design is converted into verification work, THE workflow SHALL connect proposed correctness properties to requirements, tasks and appropriate check methods. | Property request/result flow validates traceability; required outcomes remain required; unnecessary property testing is not imposed. | Required |
| REQ-005 | WHEN a scoped task plan is executed, THE workflow SHALL coordinate eligible tasks with bounded attempts, explicit authority and verification, and isolate concurrent writes. | Individual/all-task plans, overlap handling, isolated candidate and worker worktrees, declared checks, failure/timeout/unknown outcomes and current completion evidence are exercised. | Required |
| REQ-006 | WHEN a candidate run is ready to apply, THE workflow SHALL preserve the original project until explicit application and reject changed or conflicting input state. | Dirty user work is never stashed or overwritten; source/candidate identities, scope and integrated checks gate application; no force action or automatic replay. | Required |
| REQ-007 | WHEN a specification or declared input changes, THE workflow SHALL expose affected reviews, tasks and checks and require deliberate reconciliation before relying on invalidated outcomes. | Preview identifies impact and regeneration work; apply uses an expected fingerprint, preserves history, reopens invalid completion and chooses the appropriate earlier phase. | Required |
| REQ-008 | WHEN the workflow is adopted or used through supported entry commands, THE workflow SHALL preserve existing project authority and provide complete guides and packaged runtime dependencies. | Greenfield/brownfield installations and documented commands work; source changes/collisions fail before writes; no duplicate plugins or implicit native trust. | Required |
| REQ-009 | WHEN repository delivery is reported, THE workflow SHALL identify tested source, meaningful regression and integration evidence, independent findings and exact publication results. | Aggregate checks, adversarial execution fixtures, package integration, current naming/link scans and complete remote tree readback are recorded honestly. | Required |
| REQ-010 | WHEN end-to-end native runtime equivalence is claimed, THE workflow SHALL support that claim with actual selected-client consultation and execution observations. | A bounded greenfield feature and brownfield correction, changed requirement and interrupted resume are observed in the selected client; fixture results cannot substitute for these trials. | Required |

## Constraints and open boundary

The current task authorizes repository implementation, public research, local subprocess fixtures and publication. It does not waive the user's standing requirement for manual approval before additional credit-consuming code/model execution. No AWS account or deployment scope is supplied. Consequently native model trials remain an explicit unfinished acceptance gate until their concrete scope is approved; local implementation must continue to completion meanwhile.

Reviews use actual user or delegated authority. Standard phase reviews and quick combined readiness remain documented; no phase creates fictional user acceptance. Automatic execution requires an explicit reviewed execution configuration and invocation. Python remains the standard-library implementation. No daemon, external tracker replacement, pipeline replacement or new plugin installation is introduced.
