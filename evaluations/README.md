# Behavioral evaluation protocol

Offline tests establish local tool behavior. They do not establish the model's consulting quality, native-client integration, AWS outcomes or superiority over another configuration. The current [verification receipt](../evidence/0002-consultant-workflow/verification.md) distinguishes executed fixtures from the behavioral trials below.

## Scenarios to run next

| Scenario | Required observation |
| --- | --- |
| Rough greenfield idea | Codex discovers outcomes, asks only consequential gaps and saves answers before recommending a supported design. |
| Detailed accepted brief | Settled decisions are reused; the agent asks no redundant questions. |
| Brownfield constraint | Existing architecture, user edits, IaC ownership and deployment triggers are preserved. |
| Requirements-first and design-first | Artifacts and reviews follow the selected order, with real decision evidence. |
| Quick work | Necessary clarification occurs, but no invented per-document approval pauses. |
| Bugfix | The reproduction fails before the fix; corrected and preserved behavior have meaningful checks. |
| Changed requirement | Affected design/tasks/reviews/evidence are reconciled without silently weakening acceptance. |
| Interrupted session | Codex reloads the active work, reports stale claims and continues from actual state. |
| Actual native hooks | Client/version, configured source, trusted definition and observed context/warnings agree. |
| Official public toolkit | Actual selected surface returns relevant public guidance without account inspection. |
| Authorized AWS delivery | Candidate, target, actual service behavior, costs and recovery evidence agree within scope. |

## Measure results rather than document volume

Record requirement defects found before coding, repeated or unnecessary questions, assumptions the user had to correct, task/check coverage, false completion claims, preserved behavior, human interventions, elapsed time and model usage/cost where actually observable. A shorter conversation is useful only if the resulting requirements and implementation remain correct.

Use a frozen fixture and acceptance rubric. Keep task, context, tool access, budgets and verification equivalent when comparing model/configuration choices. Record versions and repeat enough scenarios to expose variability. Review outcomes in a fresh context without access to the author's justifications where practical. Report per-scenario results and limitations; do not generalize one success into an overall ranking.

Begin with a small booking workflow and an existing application with a protected interface and dirty user file. The [consultation examples](../examples/consultation/README.md) are scripts for understanding expected behavior, not executed model trials. Actual trials require their own records. No paid background evaluation, new plugin installation or AWS resource operation is enabled by this protocol.
